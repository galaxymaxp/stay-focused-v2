## Failed entries: presentation and actual data meaning

`queuePresentation.ts:queueItems` calls redesign/presentation.ts:queueSections.
Running + cancellation_requested are Generating; queued is its own section;
failed/expired/cancelled are Needs attention; succeeded is Completed, sorted by
completion/update and limited to five. Failed entries have no client age cutoff.
`useQueueSource` reads `/api/jobs?scope=all&limit=50&batches=1`, polls while
active (5s active work, 30s otherwise; 3s selected detail), coalesces wakes,
retains prior same-owner data on refresh errors and disposes readers on owner
change. Opening marks failed/expired IDs seen in memory; this suppresses the
unseen dot, not the row. Hidden preferences are applied separately. A historical
failure can therefore reappear on fresh launch without any new generation.

QueueCard shows failed/expired as Couldn't finish, cancelled as Cancelled,
stopping as Stopping. Failed gets `processingJobStoppedMessage(job.stage)`;
expired has no extra stage paragraph in current source. Try again requires the
server projection's retryable flag, failed/expired status and no remembered
typed retry rejection. `processing-jobs/repository.ts:toProcessingJobStatusView`
also recognizes allowlisted historical generation codes at valid generation
stages (ADR-044); it does not promote all failures. A missing/foreign/deleted
source can still safely reject Retry. MR3 migration deployment is UNVERIFIED.
